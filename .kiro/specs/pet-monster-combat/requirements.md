# Requirements Document

## Introduction

Este documento define os requisitos para a funcionalidade de Pet Monster em Combate. O sistema permite que um jogador controle dois personagens durante o combate online: seu personagem principal e um monstro pet. Ambas as entidades são enviadas ao servidor WebSocket e participam ativamente do combate, com o jogador controlando os turnos de ambos.

## Glossary

- **Player_Character**: O personagem principal do jogador, representado pela interface `Character` existente no sistema.
- **Pet_Monster**: Um monstro controlado pelo jogador que participa do combate como uma entidade separada, baseado na estrutura `NpcTemplate`.
- **Combat_Session**: A sessão de combate online gerenciada via WebSocket onde combatentes interagem em turnos.
- **Combatant**: A representação unificada de qualquer entidade participante do combate (jogador, NPC ou pet), conforme a interface `Combatant` existente.
- **Pet_Combatant**: A representação do Pet_Monster convertida para o formato Combatant para participação no combate.
- **Owner**: O jogador que possui e controla o Pet_Monster durante o combate.
- **WebSocket_Server**: O servidor backend que gerencia a sincronização do estado de combate entre todos os participantes.
- **Initiative_Roll**: O valor de iniciativa que determina a ordem de turno no combate.

## Requirements

### Requirement 1: Registro do Pet Monster

**User Story:** Como jogador, quero registrar um monstro como meu pet, para que eu possa utilizá-lo em combates online.

#### Acceptance Criteria

1. THE Player_Character SHALL have at most one optional Pet_Monster association stored locally via AsyncStorage under the same storage key used for the Player_Character data.
2. WHEN the player selects a monster from the NPC library, THE System SHALL allow the player to assign that monster as the Pet_Monster by copying the NpcTemplate data into the Player_Character record.
3. WHEN a Pet_Monster is assigned and the player already has an existing Pet_Monster, THE System SHALL replace the existing Pet_Monster data with the newly selected monster.
4. WHEN a Pet_Monster is assigned, THE System SHALL persist the Pet_Monster data within the Player_Character AsyncStorage entry and display a confirmation indicator to the player within 2 seconds.
5. THE Pet_Monster SHALL contain all fields required by the NpcTemplate interface: name, image, level, class, ancestry, maxHp, maxFocus, armorClass, attributes, stances, skills, spells, initiativeBonus, speed, and weapons.
6. WHEN the player removes the Pet_Monster assignment, THE System SHALL clear the Pet_Monster data from the Player_Character AsyncStorage entry and update the UI to reflect no Pet_Monster is assigned.
7. IF the AsyncStorage write fails during Pet_Monster assignment or removal, THEN THE System SHALL display an error message indicating the operation failed and retain the previous Pet_Monster state.

### Requirement 2: Conversão do Pet Monster para Combatant

**User Story:** Como jogador, quero que meu pet monster seja convertido para o formato de combate, para que ele participe corretamente da sessão online.

#### Acceptance Criteria

1. WHEN the player joins a Combat_Session and has a Pet_Monster assigned, THE System SHALL convert the Pet_Monster into a Pet_Combatant following the same field mapping as the npcToCombatant factory (NpcTemplate fields mapped to Combatant fields).
2. THE Pet_Combatant SHALL have a unique ID generated by concatenating the Pet_Monster name, an underscore separator, and the Owner player name, then applying the same safe-ID normalization (lowercase, accent removal, whitespace-to-underscore) used for other combatants.
3. THE Pet_Combatant SHALL have its type field set to "player" to indicate it is controlled by a player rather than the GM.
4. THE Pet_Combatant SHALL be initialized with hp.current equal to hp.max, focus.current equal to focus.max, turnActions all set to true, and deathSaves at zero successes and zero failures, along with its own independent armorClass, initiative, attributes, stances, skills, spells, and weapons copied from the Pet_Monster source data.
5. IF the Pet_Monster has no initiative value at the time of conversion, THEN THE System SHALL display a prompt to the player requesting a separate initiative roll for the Pet_Monster before completing the conversion.
6. IF the Pet_Monster source data is missing required combat fields (hp, armorClass, or attributes), THEN THE System SHALL reject the conversion and display an error message indicating which fields are missing, without adding the Pet_Combatant to the session.
7. IF the Pet_Monster has no weapons defined, THEN THE System SHALL assign default melee and ranged weapon data with base damage of "1d4" and an attack bonus of 0, consistent with the NPC fallback defaults.

### Requirement 3: Envio de Ambas Entidades ao Servidor

**User Story:** Como jogador, quero enviar tanto meu personagem quanto meu pet monster ao servidor, para que ambos participem do combate online.

#### Acceptance Criteria

1. WHEN the player joins a Combat_Session with a Pet_Monster assigned, THE System SHALL send a JOIN_SESSION message containing the Player_Character Combatant followed by a second JOIN_SESSION message containing the Pet_Combatant over the same WebSocket connection, completing both sends within 2 seconds of connection establishment.
2. WHEN the WebSocket_Server responds with a state synchronization containing both the Player_Character and the Pet_Combatant in the combatants list, THE System SHALL display both entities in the combat list within 1 second of receiving the acknowledgment.
3. IF the WebSocket connection closes or errors during the send of either combatant, THEN THE System SHALL display an error message indicating which combatant failed to join, preserve the player's connection form inputs, and present a retry button that re-initiates the full join sequence for both combatants.
4. IF the Player_Character Combatant is sent successfully but the Pet_Combatant send fails, THEN THE System SHALL notify the player that the pet failed to join and allow retrying the Pet_Combatant send without disconnecting the Player_Character.
5. WHEN the player reconnects to an existing Combat_Session where both entities were previously registered, THE System SHALL send both the Player_Character and the Pet_Combatant in the reconnection sequence, using the initiative values previously stored on the server.
6. IF the player joins a Combat_Session without a Pet_Monster assigned, THEN THE System SHALL send only the Player_Character Combatant and proceed with the standard single-combatant join flow.

### Requirement 4: Controle de Turno do Pet Monster

**User Story:** Como jogador, quero controlar as ações do meu pet monster durante o turno dele, para que eu possa usar suas habilidades no combate.

#### Acceptance Criteria

1. WHEN the active turn belongs to the Pet_Combatant, THE System SHALL display the ActiveTurnInterface with the Pet_Combatant data (skills, spells, stances, weapons) exclusively to the Owner.
2. WHILE the Pet_Combatant turn is active, THE System SHALL allow the Owner to use standard actions, bonus actions, and reactions from the Pet_Combatant available actions (skills, spells, stances, and weapons), consuming the corresponding turnAction type (standard, bonus, or reaction) upon use.
3. IF the Owner attempts to use an action type (standard, bonus, or reaction) that has already been consumed for the Pet_Combatant in the current turn, THEN THE System SHALL prevent the action and display an alert message indicating the action is unavailable.
4. WHEN the Owner performs an action with the Pet_Combatant, THE System SHALL send the action to the WebSocket_Server via the RESOLVE_ACTION message with the Pet_Combatant ID as the attackerId.
5. THE System SHALL track the Pet_Combatant turnActions (standard, bonus, reaction) independently from the Player_Character turnActions, so that consuming an action on one does not affect the other.
6. WHEN the Owner ends the Pet_Combatant turn, THE System SHALL send an END_TURN message with the Pet_Combatant ID and reset the Pet_Combatant turnActions (standard, bonus, reaction) to available.
7. IF the WebSocket_Server fails to process a Pet_Combatant action, THEN THE System SHALL display an error message to the Owner and preserve the Pet_Combatant turnActions state prior to the failed action.

### Requirement 5: Exibição do Pet Monster na Interface de Combate

**User Story:** Como jogador, quero visualizar o estado do meu pet monster durante o combate, para que eu saiba seus HP, foco e condições atuais.

#### Acceptance Criteria

1. WHILE the Combat_Session is active, THE System SHALL display the Pet_Combatant in the combatants list as a SpectatorCard with a label indicating the Owner name followed by "(Pet)" appended to the Pet_Combatant name.
2. WHEN the Pet_Combatant receives damage or healing, THE System SHALL display a CombatNotification to the Owner showing the notification type (damage or heal), the source name, the skill name, and the numeric value in PV.
3. IF a CombatNotification for the Owner is already visible when the Pet_Combatant receives damage or healing, THEN THE System SHALL replace the current notification with the new Pet_Combatant notification.
4. WHILE the Pet_Combatant turn is active, THE System SHALL display the Pet_Combatant current HP, max HP, current focus, max focus, and armor class in the ActiveTurnInterface.
5. WHEN the Pet_Combatant HP reaches zero, THE System SHALL display the DeathSaveMonitor component for the Pet_Combatant showing successes and failures counters.
6. WHILE the player is spectating (not their turn), THE System SHALL show the Pet_Combatant as a SpectatorCard in the combatants list positioned adjacent to the Player_Character SpectatorCard.
7. WHILE the player is spectating, THE System SHALL display the Pet_Combatant HP as an exact percentage for the Owner and as a descriptive health status label for other players.

### Requirement 6: Iniciativa Separada para o Pet Monster

**User Story:** Como jogador, quero rolar iniciativa separadamente para meu pet monster, para que ele tenha sua própria posição na ordem de turno.

#### Acceptance Criteria

1. WHEN the player connects to a new Combat_Session with a Pet_Monster, THE System SHALL display an initiative modal for the Pet_Monster after the Player_Character initiative is confirmed, displaying the Pet_Monster name in the modal title.
2. WHEN the player presses the roll button in the Pet_Monster initiative modal, THE System SHALL generate a random d20 result (1–20) and add the Pet_Monster initiativeBonus to produce the final initiative value.
3. WHEN the player manually inputs the Pet_Monster initiative value, THE System SHALL accept only integer values between 1 and 30.
4. WHEN the player confirms the Pet_Monster initiative value, THE System SHALL place the Pet_Combatant in the turn order independently based on its own initiative value, separate from the Player_Character position.
5. IF the Pet_Monster initiative equals another combatant's initiative, THEN THE System SHALL use the standard tie-breaking rules defined by the WebSocket_Server.
6. IF the player dismisses the Pet_Monster initiative modal without confirming a value, THEN THE System SHALL keep the modal displayed until a valid initiative value is confirmed.

### Requirement 7: Reação do Pet Monster

**User Story:** Como jogador, quero poder usar reações do meu pet monster fora do turno dele, para que ele possa se defender ou contra-atacar.

#### Acceptance Criteria

1. WHILE the active turn does not belong to the Pet_Combatant, IF the Pet_Combatant turnActions.reaction is true, THEN THE System SHALL display a ReactionOverlay for the Pet_Combatant showing the opportunity attack option and any skills with actionType containing "reação" or "reaction".
2. WHEN the Owner triggers a reaction for the Pet_Combatant, THE System SHALL send a RESOLVE_ACTION message to the WebSocket_Server with the Pet_Combatant ID as attackerId and costType set to "reaction".
3. WHEN the Pet_Combatant reaction is used, THE System SHALL set the Pet_Combatant turnActions.reaction to false for the current round and hide the Pet_Combatant ReactionOverlay.
4. THE System SHALL display the Pet_Combatant ReactionOverlay as a separate overlay instance from the Player_Character ReactionOverlay, so that both can be visible simultaneously without overlapping each other.
5. WHEN the Pet_Combatant turn starts, THE System SHALL reset the Pet_Combatant turnActions.reaction to true.
6. IF the Owner triggers a reaction skill for the Pet_Combatant and the Pet_Combatant current focus is less than the skill cost, THEN THE System SHALL display an alert indicating insufficient focus and SHALL NOT consume the reaction.

### Requirement 8: Desconexão e Persistência do Pet Monster no Combate

**User Story:** Como jogador, quero que meu pet monster persista na sessão de combate mesmo se eu desconectar temporariamente, para que eu não perca o progresso dele.

#### Acceptance Criteria

1. WHEN the player disconnects from the Combat_Session, THE WebSocket_Server SHALL maintain both the Player_Character and Pet_Combatant state for a maximum of 300 seconds (5 minutes).
2. WHEN the player reconnects within the 300-second retention window, THE System SHALL synchronize the current state of both the Player_Character and Pet_Combatant from the WebSocket_Server and display both entities in the combat interface with their updated values (HP, focus, turnActions, deathSaves).
3. IF the player disconnects during the Pet_Combatant turn or the Player_Character turn, THEN THE WebSocket_Server SHALL skip the disconnected player's combatant turns until the player reconnects.
4. THE System SHALL identify the Pet_Combatant as belonging to the Owner using the combined ID pattern (Owner name + Pet_Monster name).
5. IF the player does not reconnect within the 300-second retention window, THEN THE WebSocket_Server SHALL remove both the Player_Character and Pet_Combatant from the Combat_Session.
